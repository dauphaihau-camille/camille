# The API Contract Is A Published Spec Package

## Status

Accepted

## Context

Camille splits the product across two repositories: the Nest API in `apps/api` and the web client in `apps/web`. They ship independently, so the HTTP contract between them is a real interface with its own release cadence.

Before this decision the contract existed only as Nest decorators and inferred TypeScript types. The web client consumed shapes it could not verify, and no artifact recorded what the API promised. Drift surfaced as runtime failures in the browser rather than as review comments.

The contract also has to be generated, not authored. Nest controllers, DTOs, and validation decorators are the source of truth; a parallel document maintained by hand is a second source of truth that decays.

The contract covers the versioned REST surface the web client calls: request and response shapes for the `/v1` endpoints, their parameters, status codes, and declared media types. It does not cover internal service boundaries, queue payloads, or database schema. Those change freely inside the API.

Publishing the document as a package gives the web side something to depend on with ordinary package semantics: a version, a pin, and an install that either succeeds or fails. It avoids coupling the two repositories at the source level while still letting the web compile against real API shapes.

## Decision

The API contract is one committed OpenAPI document, `apps/api/api/openapi.json`, generated from the compiled Nest application in preview mode. Preview mode runs without PostgreSQL, Redis, MinIO, or MongoDB, so generation is a pure build step that any reviewer can reproduce. The document is never hand-edited; it is regenerated by `apps/api/api/scripts/generate-openapi.ts` and changes appear as reviewable diffs.

The document is published as `@dauphaihau-camille/api-spec` on GitHub Packages. A publish carries the OpenAPI document and the bump version it implies. The web repository pins an exact version of the package and commits the generated `apps/web/packages/shared/src/api/generated/openapi.d.ts`.

Both sides refuse stale artifacts in CI. The API verifies the committed document matches a fresh generation, and the web verifies its committed declaration file matches a regeneration from the pinned package. The API additionally compares the candidate document against the last published package before merge and again before publish, using `apps/api/api/scripts/check-contract-breaking.mjs`; `--baseline-spec` with `--baseline-version` points the same check at a local document when the registry is unreachable.

Bump magnitude is derived from that comparison: an ERR finding requires a major version, a WARN finding or additive structure requires a minor version, and documentation-only changes take a patch version.

The root `./scripts/verify` entry point exposes the contract as four targets: `api` for the Nest lint, typecheck, and unit tests, `spec` for document freshness plus the packaged copy inside the workspace, `api-types` for regenerating the web declaration file against the pinned package and diffing it, and `contract` for the breaking comparison against the last published package.

The package ships only the generated document. Its version lives in `apps/api/packages/api-spec/package.json` and moves in the same change as the document, so a contract change is never published under an unchanged version. The web side regenerates its declaration file from the pinned package through `generate:api-types`.

These checks are gates, not advisories. A stale document, a stale declaration file, or an ERR finding against the baseline blocks merge; the breaking comparison runs again before publish so a version cannot be published with the wrong magnitude. Publishing happens after merge, so the web can only pin a document that already passed the gates.

## Consequences

- Contract changes are reviewable diffs in `apps/api/api/openapi.json` rather than unstated behavior changes in controller code.
- The web build needs GitHub Packages access, including a `read:packages` token, to install the spec package.
- A merged API change reaches the web only through a version bump and a pin update. The web does not track API `main`.
- Preview-mode generation is a hard requirement of the toolchain. Generation that needs a live database is not a supported path, because the contract must be reproducible in CI and on a bare checkout.
- The error envelope is modelled separately from success schemas. Controllers declare success responses; the shared failure shape is described once, so every endpoint reports errors the same way.
- The bump policy is mechanical, so version numbers carry information: consumers can read a major bump as a breaking change rather than guessing from release notes.
- Shape mismatches become compile errors in the web build instead of runtime failures in the browser.
- In the superproject both repositories are checked out at once, so the web type check reads the API's committed document when the package is not installed and the pinned package once it is. Both paths must produce the same declaration file, which the freshness checks enforce.

## Alternatives Considered

### Fetch `/docs/openapi.json` from a running API at build time

Rejected. It makes the web build depend on a reachable API deployment, pins the web to whatever the environment happens to run, and gives no reviewable artifact.

### Hand-maintained zod types shared between the repos

Rejected. It duplicates the contract already expressed by Nest decorators and validation pipes, and the two copies drift silently. A generated document keeps one source of truth.

### Generate types at install time from the published package

Rejected. Generated output would appear only after an install, so CI could not diff it and reviewers could not see contract changes in a pull request. Committing the declaration file makes drift visible.

### Design-first, hand-authored YAML

Rejected. It inverts the source of truth: the spec would be written first and controllers would follow it by convention only. Nest already holds the implementation truth, and a hand-authored document drifts from it with no automated check.
